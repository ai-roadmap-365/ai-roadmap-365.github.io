# Week 21 project — First End-to-End Model

This week was **Machine Learning Fundamentals**: what learning from data is
and is not, the three shapes of feedback, the workflow with contracts between
its stages, why a dataset needs three splits and not two, the arithmetic that
turns overfitting and underfitting into two named quantities, the
scikit-learn API, and finally a walked-through classification exercise on the
iris dataset.

Day 147 walked you through that exercise with the course narrating every
decision. This project takes the narration away. You still work with iris —
it is small, bundled with scikit-learn, and fully offline — but every choice
that Day 147 made out loud, you now make yourself and write down: the metric
before the model, the majority baseline before either, a three-way split with
the unit of independence named, a sweep whose optimism you compute in advance
rather than discover after the fact, exactly one look at the test set, and a
written verdict that is willing to say "I cannot tell the difference" when
that is what thirty rows can support.

**Environment:** scikit-learn 1.9.0, NumPy 2.5.2 and scipy 1.18.1, the same
versions Day 144's lab measured its selection-optimism table on. No GPU is
needed and none is used — every model in this project fits in well under a
second on a laptop CPU. The dataset ships inside scikit-learn
(`sklearn.datasets.load_iris`), so the whole project runs with no network
access at all.

**Safety, because this runs on your own machine:** everything the steps below
ask you to do writes only inside your own project directory, installs
nothing into system Python, needs no `sudo`, and reaches no network. If you
create a virtual environment, create it inside your project directory or
somewhere else under your own control — never point it at anything outside
that directory.

## What you are building

One small project directory whose deliverable is `REPORT.md`, generated by a
script rather than typed by hand — the Day 126 discipline in miniature: a
number in your prose and a number in your confusion matrix must be the same
number, computed in the same run.

```
iris-model/
  data/                # nothing to fetch — sklearn.datasets ships iris
  src/
    baseline.py         # majority-class baseline, computed first
    split.py             # the three-way stratified split
    sweep.py              # the candidate sweep + selection-optimism arithmetic
    evaluate.py            # the single test-set evaluation + interval
    error_analysis.py       # confusion matrix + the concrete next step
    render.py                 # writes REPORT.md from computed values only
  run_project.py        # entry point: baseline -> split -> sweep -> evaluate -> render
  REPORT.md              # the deliverable, generated
  manifest.json            # seed, versions, split sizes, K, hashes
```

If you prefer a single notebook, that is fine, on the same terms Day 139
set: it is judged by whether **restart-and-run-all** reproduces the whole
thing, not by whether it happened to run once in the order you clicked.

## Requirements

Each of these traces to a specific day. Do them in the order given — the
order is not incidental, it is the point.

1. **State the target, the metric, and the baseline, before touching a
   model** (Day 143). Write one paragraph: what you are predicting (the
   iris species, three classes, balanced at 50 rows each), what metric you
   will report (accuracy is defensible here because the classes are
   balanced — say so explicitly, because on an imbalanced problem Day 143
   showed accuracy and recall shipping different models), and what
   "better than nothing" means before you have measured it.

2. **Compute and report the majority-class baseline first** (Day 143). On
   balanced iris this baseline is close to one in three. Report it with its
   95% interval (Requirement 6's formula, applied to the baseline itself)
   before you fit a single classifier. A model that cannot clear this bar
   with margin to spare has not learned the species from the measurements —
   it has learned to imitate the most common label.

3. **A three-way split, stratified, with the unit of independence named**
   (Day 144). Iris has no repeated measurements of the same flower and no
   natural grouping — one row is one flower, measured once — so the unit of
   independence is the row itself, and a plain stratified row-wise split is
   the right tool. Say this in your report explicitly, rather than silently
   assuming it: a dataset where the same physical unit produces several rows
   (repeated sensor readings, several loans from one applicant) would need a
   **group-aware** split instead, and Day 144 measured what happens when
   that distinction is missed — an accuracy of 0.9760 that a group-aware
   split corrected to 0.4112. Iris does not have that problem, but your
   report should say why it does not, not just that it does not.

4. **Every fitted transform lives inside a `Pipeline`** (Day 146). If you
   scale features, the `StandardScaler` goes in the pipeline with the
   classifier, not applied once to the whole dataset before the split. A
   scaler fitted on the full dataset has seen the test rows' distribution
   before the test evaluation happens, which is a narrow but real form of
   the leakage Day 143 built a whole stage-contract system to catch.

5. **A model-selection sweep with the optimism computed before you look at
   the test set** (Day 144). Try at least four candidates — different values
   of a hyperparameter, or different model families, or both — and pick the
   winner by validation-set score alone. Before you touch the test set,
   count your candidates as **K**, compute the validation set's standard
   error (`sqrt(p(1-p)/n_val)`), and multiply it by the expected maximum of
   K standard normal draws — Day 144's own simulated table, not the
   `sqrt(2 ln K)` closed form, which that day's lab measured as running
   consistently high. Write this number down in your report *before* the
   test-set step below, as a stated expectation, not a post-hoc excuse.

6. **Exactly one test-set evaluation, with a 95% interval** (Day 144).
   Score your chosen pipeline on the test set once. Report the accuracy with
   a 95% interval computed as `accuracy ± 1.96 * sqrt(accuracy * (1 -
   accuracy) / n_test)`. If you evaluate a second candidate on the test set
   to "double check," you have turned the test set into a second validation
   set, and every honest thing your report says about the interval is now
   false — Day 144's `TestSetTouchedTwice` guard exists for exactly this.

7. **An error analysis that names a concrete next step** (Day 147). Produce
   the confusion matrix. Say which classes get confused with which, and
   whether that confusion matches what a biologist would expect from the
   measurements (iris versicolor and iris virginica overlap in petal
   measurements in ways setosa does not — if your matrix shows that
   pattern, say so; if it does not, say what it shows instead). The next
   step must be something other than "try a better model" — more features,
   more data for the confused pair, a look at the specific misclassified
   rows, or a stated decision to accept the error rate as it stands and why.

8. **A written verdict, 300 to 500 words** (the whole week, applied at
   once). State plainly whether your model beats the baseline by more than
   the two intervals combined can explain by chance, using the actual
   numbers you computed — not "it did better," a number and its interval.
   If two things you compared are closer together than their intervals'
   combined width, say **"I cannot distinguish these on this test set"**
   rather than picking a winner anyway. On iris, with a 30-row test set,
   this will usually happen if you compare two *good* models to each other;
   it will usually *not* happen when you compare your model to the
   near-random baseline, because that gap is large. Say which case you are
   in and why.

9. **A reproducibility artefact** (Day 126, Day 139). Pin your package
   versions, set and record a random seed, and rerun `run_project.py` (or
   restart-and-run-all your notebook) from a clean state. Confirm the
   second run produces the same split sizes, the same chosen candidate, and
   the same test accuracy as the first, and say in your report that you
   checked this.

## Steps

1. Load iris with `sklearn.datasets.load_iris`. Write the target, metric and
   baseline paragraph (Requirement 1) before you write any code that fits a
   model.
2. Split into train/validation/test with `train_test_split`, stratified,
   twice (once to carve off the test set, once to carve validation from what
   remains). Name the unit of independence in the report (Requirement 3) at
   this point, while you are looking straight at the decision.
3. Compute the majority-class baseline on train, and its accuracy on both
   validation and test, with intervals (Requirement 2).
4. Build your candidates as `Pipeline` objects (Requirement 4). At least
   four — try varying `n_neighbors` in `KNeighborsClassifier`, and compare
   at least one different model family such as `LogisticRegression` or
   `DecisionTreeClassifier`, so the sweep is not just one hyperparameter on
   one algorithm.
5. Score every candidate on the validation set. Count K, compute the
   validation standard error, and multiply by the expected maximum of K
   normals from Day 144's table (or your own simulation of it) to get your
   selection optimism (Requirement 5), before doing anything else.
6. Pick the validation winner. Evaluate it on the test set **once**
   (Requirement 6). Compute the 95% interval.
7. Build the confusion matrix on the test predictions. Write the error
   analysis and the concrete next step (Requirement 7).
8. Write the 300-500 word verdict (Requirement 8), citing the actual numbers
   from steps 3 and 6.
9. Move every number in `REPORT.md`'s prose into `render.py` as a formatted
   computed value. Run `run_project.py` twice from a clean state and confirm
   the results match (Requirement 9).

## Expected output

The numbers below are from one real run of this project, seeded, on a
90/30/30 stratified split of the 150-row iris dataset (30 rows per class in
train, 10 per class in validation, 10 per class in test). **Your own numbers
will differ** — a different seed produces a different split, a different
winning candidate, and a different test accuracy — but the shapes below
(a baseline reported with an interval, a sweep with a computed optimism, one
test evaluation with its own interval, a confusion matrix with a named
pattern) are what a correct report contains regardless of seed.

**Baseline.** 150 rows, three classes of 50 each, so the majority-class
baseline is exactly 1/3 on every split. On the 30-row test set that is
`0.3333`, with a 95% interval of `0.3333 ± 1.96 * sqrt(0.3333 * 0.6667 / 30)
= 0.3333 ± 0.1687`, i.e. roughly `[0.165, 0.502]`.

**Sweep.** Ten candidates: `KNeighborsClassifier` at `n_neighbors` in {1, 3,
5, 7, 9, 11, 15, 21}, plus `LogisticRegression` and a depth-3
`DecisionTreeClassifier`, each wrapped in a `Pipeline` with a
`StandardScaler` (the tree does not need scaling, but wrapping it costs
nothing and keeps every candidate built the same way). So `K = 10`. The
winning candidate on validation was 1-nearest-neighbour, at a validation
accuracy of `0.9333` (28/30). The validation set's standard error at that
accuracy is `sqrt(0.9333 * 0.0667 / 30) = 0.0455`. Day 144's simulated
table gives the expected maximum of 10 standard normal draws as
approximately `1.54` (the `sqrt(2*ln(10)) = 2.15` closed form is the
looser, too-high figure that day's lab measured and rejected). Selection
optimism: `0.0455 * 1.54 ≈ 0.070`. In plain language: a validation score of
`0.9333` earned by the best of ten candidates should be expected to
overstate the candidate's real accuracy by roughly seven points once you
look elsewhere — and that is exactly the direction the test result went.

**Test evaluation.** The chosen pipeline scored `0.8333` (25/30) on the
test set, evaluated once. Its 95% interval: `0.8333 ± 1.96 * sqrt(0.8333 *
0.1667 / 30) = 0.8333 ± 0.1334`, i.e. `[0.700, 0.967]`. The gap between the
`0.9333` validation figure and the `0.8333` test figure is `0.10` — close to
the `0.070` optimism budgeted for in advance, which is the point of
computing that number before looking: it turns a disappointing-feeling drop
into an anticipated one.

**Baseline versus model.** The model's interval `[0.700, 0.967]` and the
baseline's interval `[0.165, 0.502]` do not overlap at all, and the gap
between the two point estimates (`0.8333 - 0.3333 = 0.50`) is roughly three
times either interval's own half-width. This is a case the intervals can
resolve: the model beats the baseline, comfortably, on this evidence.

**Error analysis.** Confusion matrix on the 30 test rows (rows are true
class, columns are predicted class, order setosa / versicolor /
virginica):

```
              pred:setosa  pred:versicolor  pred:virginica
true:setosa            9                1               0
true:versicolor        0                8               2
true:virginica          0                2               8
```

All five errors involve versicolor and virginica — the two species whose
petal measurements are known to overlap — except one setosa row
misclassified as versicolor, which is the less expected error and is worth
a specific look at that row's measurements rather than a shrug. A concrete
next step: pull the five misclassified rows and check whether they sit near
the versicolor/virginica decision boundary in petal length and width, which
would confirm the confusion is a real measurement overlap rather than a
labelling or preprocessing bug; the stray setosa error is worth checking
separately, since setosa is normally perfectly separable from the other two
on petal measurements alone.

**Verdict shape (not the words to copy).** A correct verdict states the
model's test accuracy and interval, states the baseline's, says the two do
not overlap and are three interval-widths apart, and concludes the model
has learned something real about the species from the four measurements —
while also saying, honestly, that the *specific* 0.8333 figure has a wide
enough interval (`[0.700, 0.967]`) that a second seed producing 0.90 or
0.77 would not be surprising, and that comparing this model to a *different
strong candidate* (rather than to the near-random baseline) would very
plausibly land inside that same interval and be unresolvable on 30 rows.

      fit, and states why accuracy is defensible on this dataset.
- [ ] The majority-class baseline is computed (not assumed) and reported
      with a 95% interval.
- [ ] The split is stratified and three-way, and the report names the unit
      of independence and says why a plain row-wise split is correct for
      iris specifically.
- [ ] Every candidate is a `Pipeline`; no transform is fitted on data outside
      its own fold.
- [ ] At least four candidates were swept, K is stated, and the selection
      optimism (`validation SE × E[max of K normals]`) is computed and

- [ ] The test set is evaluated exactly once. If the report or the code
      shows a second test-set score for a different candidate, this fails
      regardless of how the numbers turned out.
- [ ] The test accuracy is reported with a 95% interval using
      `sqrt(p(1-p)/n)`, and the arithmetic is shown, not just the result.
- [ ] The confusion matrix is present, the confused classes are named, and
      a next step is proposed that is not "try a better model."
- [ ] The written verdict is 300-500 words, states whether the model beats
      the baseline by more than the intervals can explain by chance, and is

- [ ] A seed is recorded, and rerunning the project from a clean state

## Troubleshooting

- **Your test accuracy came back at exactly 1.0, with a zero-width
  interval.** This happens on iris more often than intuition expects — it
  is a small, well-separated dataset, and a 30-row test set is small enough
  that "no errors" is a plausible real outcome, not necessarily a sign
  something is wrong. The Wald interval's `sqrt(p(1-p)/n)` genuinely goes
  to zero at `p = 1`, which is a known weakness of that formula at the
  boundary rather than a claim that a perfect model has zero uncertainty.
  Say so explicitly in your report rather than presenting `[1.000, 1.000]`
  as if it meant your model is guaranteed to be perfect on the next thirty
  flowers — it does not mean that, and a single misclassified row on a
  different seed would move the estimate a long way.

- **You compared two close candidates on the test set to "make sure," and
  now both numbers are test scores.** The test set has been touched twice,
  and Requirement 6 is broken regardless of which candidate you report.
  There is no repair that keeps both numbers honest. Either report only the
  first evaluation and discard the second as a validation-only comparison
  you should not have run against test data, or — the more honest option —
  say plainly in the report that the test set was used twice, name which
  score you are actually relying on, and note that the reported interval no
  longer has its usual guarantee.

- **Your validation winner and your test winner are different models.**
  This is not a bug to fix by re-picking on the test set (see above). It is
  the selection-optimism phenomenon showing up in an unusually visible way:
  the validation set's luckiest candidate is not always the test set's
  best, especially at 30 validation rows. Report the validation winner's
  test performance as your one honest evaluation, and mention the
  discrepancy in your verdict as evidence for, not against, the point about
  small validation sets.

- **Your `StandardScaler` was fitted on the whole dataset before the
  split.** The fix is not to refit it "correctly" after the fact and quietly
  swap the number — the fix is to move it inside the `Pipeline` and rerun
  everything downstream, because every score you have already computed was
  produced by a pipeline that had partially seen the test rows. Rerun from
  the split step, and note in the report that you caught and fixed this.

- **Your selection-optimism figure and your validation-to-test gap do not
  match closely.** They are not supposed to match exactly — the optimism
  formula gives the *expected* inflation across many hypothetical splits,
  and any one run is a single draw from that distribution, so it can land
  well above or below the expectation. What matters is that you computed
  the expectation *before* looking at the test result, so you can honestly
  say whether the actual drop was in the range you had budgeted for or was
  a surprise worth a second look.

- **Your written verdict says "Model A beat Model B by two points" and both
  numbers came from validation, not test, or the two-point gap is smaller
  than either model's interval half-width.** This is the mistake the whole
  project is built to catch. Two points on thirty rows is well inside the
  noise a 95% interval already describes — recompute the interval for the
  gap itself (or just check whether it is smaller than either model's own
  half-width) and, if it is, rewrite the sentence as "the two models cannot
  be distinguished on this test set," which is a complete and correct
  finding, not a hedge.
