# Day 074 — Mocking and Testing Boundaries

The fourth lesson of Week 11 ("Testing and Code Quality"), and the day the
week's techniques meet real code. Days 71 to 73 assumed the thing under test
was a function you could call with values and check the answer of. This lesson
handles the case where it is not: code that reads the clock, calls a network,
writes a file, generates a random identifier, reads the environment, or — the
case the whole course is heading toward — sends a prompt to a language model.

The lesson is deliberately opinionated, because mocking is the most misused
technique in testing. The first half teaches it properly: the five test doubles
from Meszaros's taxonomy, `unittest.mock` in depth, the patch-target rule that
costs everybody an afternoon, and a captured demonstration of an un-specced
`Mock` accepting a misspelled method so a test passes while production raises
`AttributeError`. The second half argues that the first half is usually the
wrong tool, and that the better move is to move the boundary — dependency
injection, exactly as Day 70's pure domain core did, proved the same way by
running the core from an empty directory.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout
from central configuration — never hard-code repository or site URLs inside
content files.

Keep that labelling if you edit them; do not present them as captured output.
