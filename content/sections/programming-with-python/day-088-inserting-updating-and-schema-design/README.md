# Day 088 — Inserting, Updating, and Schema Design

The fourth day of Week 13 ("SQL and Relational Databases"). Days 85 to 87 were
about reading: the relational model and SQLite, then `SELECT` with filtering and
grouping, then keys, relationships and joins. All of it was safe, because the
worst a wrong `SELECT` can do is give you a wrong answer.

Today the reader changes data, and that symmetry breaks. So the lesson is
equally about writing and about not destroying, and it opens with the single
most expensive statement in SQL — `UPDATE loans SET returned = 1;` with the
`WHERE` clause forgotten — measured against a real twelve-row table: one row
intended, twelve changed, eleven silently wrong with a plausible value.

The through-line: **make the wrong thing impossible, and make the risky thing
reversible.** A constraint does the first, a transaction does the second, a
migration does both to the schema.

Coverage: every useful form of `INSERT` (single, multi-row, `INSERT INTO
SELECT`), `RETURNING`, `UPSERT` via `ON CONFLICT DO UPDATE` and why it differs
from insert-then-update; `UPDATE` with an expression and with a correlated
subquery; `DELETE` and the reversible soft-delete alternative; transactions
properly, including the rollback journal, the byte-for-byte proof, and the
behaviour almost everybody has backwards — that a constraint error undoes only
the failing statement and leaves the transaction open, so a later `COMMIT` keeps
what already succeeded; constraints as executable documentation; application
validation versus schema constraints and why the schema wins ties; foreign keys
with `CASCADE` versus `RESTRICT`, and the fact that `PRAGMA foreign_keys` is off
by default; normalization through first, second and third normal form with a
concrete before-and-after on the library schema, then deliberate
denormalization; generated columns; `STRICT` tables; SQLite's genuinely limited
`ALTER TABLE` and the documented create-copy-drop-rename rebuild.

The A14 from-scratch artefact is a **migration runner** in about 150 lines,
tracking `PRAGMA user_version`, applying each migration and its version bump in
one transaction, idempotent on re-run — verified atomic by breaking a migration
on purpose.

The AI thread closes the day: a training-data table without constraints will
accept a duplicated example, a null label and a leaked test row, silently. The
model gets blamed months later. Data quality is a schema decision.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with it:
the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

`assets/transaction-flow.svg` is an **animated** SVG per amendment A30. It is
referenced as an ordinary image, so the browser renders it as an image document:
no scripts run and no external resources load, but CSS and CSS media queries do.
The animation is therefore written in CSS `@keyframes` rather than SMIL, and it
ships a `@media (prefers-reduced-motion: reduce)` block that stops every
animation and restores the resting state. Every class, id and `@keyframes` name
in both SVGs is prefixed (`d088a-` for the architecture diagram, `d088f-` for
the flow diagram) so that inlining several days' diagrams into one exported
page cannot collide.
