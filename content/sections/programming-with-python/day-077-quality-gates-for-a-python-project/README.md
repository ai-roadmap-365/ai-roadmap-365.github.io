# Day 077 — Quality Gates for a Python Project

The capstone lesson of Week 11 ("Testing and Code Quality"). Days 71 to 76
introduced the pieces one at a time — pytest, fixtures and parametrization,
test-driven development, mocking at boundaries, mypy, Ruff. Today assembles all
six into a single `check.sh`: one command, runnable identically on a laptop and
on a build server, returning one exit code meaning "safe to merge".

The lesson covers what a gate is and what it is not, the ordering of stages
argued from the cost of feedback, the fail-fast versus report-everything
trade-off, what each stage can and cannot prove, coverage at length and
honestly (including a real capture of 100% coverage produced by a test file
with zero assertions over a module with a real bug), one `pyproject.toml`
instead of five dotfiles, pre-commit hooks and what belongs in them, a complete
continuous-integration workflow explained line by line, the build matrix, and
branch protection as the thing that makes the verdict binding. The last third
is judgement rather than mechanism: which gates pay for themselves, the cost of
a slow gate measured in developer attention, why flaky tests must be fixed or
deleted rather than retried, the ratchet strategy for adopting a gate in a
messy codebase, and who the gate is really for.

The AI connection closes the week: as more code is generated rather than typed,
the gate is where trust is actually established — a mechanical contract
reviewable once and enforced forever — and the same structure reappears later
in the course as evaluation pipelines for models.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.
