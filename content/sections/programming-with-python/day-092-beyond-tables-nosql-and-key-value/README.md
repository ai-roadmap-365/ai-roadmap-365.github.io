# Day 092 — Beyond Tables: NoSQL and Key-Value Stores

The first lesson of Week 14 ("Data Formats and Pipelines"), and the bridge out
of Week 13's relational material. Days 85 to 91 built the relational model up
to a designed schema and a printed report. This day asks the question that
follows it honestly: what else is there, what does each alternative actually
give up, and when is giving that up the right call.

The organising idea, and the sentence most introductions to this topic do not
say: **"NoSQL" is not one thing, and it is not the opposite of SQL.** It is a
label attached to four largely unrelated families — key-value, document,
wide-column and graph — each of which drops one guarantee the relational model
provides in exchange for something else. So "SQL or NoSQL?" is not a question.
The two questions that replace it are: *which guarantee am I giving up*, and
*do I need it*.

The lesson runs one library record through all four shapes, states the
trade-offs precisely rather than as slogans, gets the CAP theorem right, and
lands on the conclusion most teams should act on: JSON inside a relational
database is the pragmatic middle path, and on a stock SQLite it costs nothing
to try.

Two things carry the day's weight. The **from-scratch document store** — put,
get, delete, find-by-field and an expression index, in seventy lines over
`sqlite3` — which exists so the reader stops treating a document database as
magic, and whose second half runs the four things it does *not* give you. And
the **schema-on-read demonstration**: one document with its title field spelled
`titel`, written into four stores, accepted by three of them, and invisible to
the catalogue query in all four. Not an error. Not an empty database. A report
that is quietly one book short. That silence is the lesson, and the lab asserts
both halves of it — the document is stored, *and* the query returns nothing —
because either half alone would also be true of a store that had rejected the
write.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the layout
from central configuration; never hard-code repository or site URLs inside
content files.

`partition-choice-flow.svg` is animated with CSS `@keyframes` inside the file,
so it animates wherever it is rendered as an image and prints as a still. It
carries a `@media (prefers-reduced-motion: reduce)` block that disables every
animation and restores the resting state, and the still frame carries the whole
meaning on its own — both branches, both consequences and the closing panel are
present without motion. Both SVGs prefix every class, id and keyframes name —
`d092a-` in the architecture diagram, `d092f-` in the flow diagram — because an
inlined SVG's `<style>` block is not scoped to that SVG and `url(#name)`
resolves document-wide, so two diagrams on one page would otherwise restyle
each other.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler — if a fact or figure is not verified, leave it out rather than approximating it.
- **The honesty boundary of this day is unusual and must be preserved.** Only SQLite, Python's `dbm` and the lab's own document store were run. Redis, Memcached, MongoDB, CouchDB, Cassandra, HBase, Neo4j and DynamoDB were **not installed and no server was available**, so the lesson describes them from their documentation and reproduces **no output** from any of them. It says so explicitly in the Alternatives section and in the lab README. Never add a transcript, a benchmark or a latency figure for any of them.
- Every output shown in this lesson is captured from a real run on the authoring machine on 2026-08-16, offline: macOS 26.5.2 (Apple Silicon, arm64), Python 3.14.0, bash 3.2.57, the `sqlite3` shell 3.51.0 and the SQLite library 3.53.3 inside Python. The captures live in the lab's `expected-output/` directory; if you change a number here, re-run the lab and change it there too.
- The two timing figures — 5.779 ms unindexed against 0.066 ms indexed, a ratio of 88x — are one machine on one day, and the lesson says so; a repeat run gave 95x. Do not present them as a constant, and do not let any test assert a millisecond value. What is stable is the plan changing from `SCAN` to `SEARCH`.
- The SQLite version claim is checked: the JSON functions became built-ins and the `->` and `->>` operators were added in **3.38.0, released 22 February 2022**, verified against the SQLite release history. Re-verify before changing it.
- The CAP statement is the load-bearing correctness claim of the lesson. It is a result about behaviour **during a partition**, it is not "pick two of three", nobody chooses P, and with no partition a store gives C and A together. Brewer stated it as a conjecture at PODC 2000, Gilbert and Lynch proved it in 2002, and Brewer corrected the popular reading himself in 2012. Do not soften this into the usual triangle.
- The schema-on-read demonstration is the day's sharpest argument. The document is accepted **and** invisible, and both halves must stay asserted — a store that rejected the write would also return zero rows, so testing only the silence proves nothing.

Licence terms for the commercial and source-available products change often and differ between server, drivers and managed offerings; the lesson deliberately declines to quote them and points the reader at each project's own site instead. Keep it that way.
