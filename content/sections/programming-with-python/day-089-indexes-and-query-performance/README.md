# Day 089 — Indexes and Query Performance

The fifth lesson of Week 13 ("SQL and Relational Databases"). Day 85 previewed
one `EXPLAIN QUERY PLAN` output and promised an explanation; this is it.

The organising idea: **an index is a second, sorted copy of one or more columns,
kept in a B-tree, with a pointer back to the row.** Everything else in the
lesson is derived from that sentence — why it makes reads fast, why it makes
writes slower, why it costs disk, and why the planner sometimes refuses to use
the one you built.

The through-line of the day is measurement discipline. Every figure in the
lesson comes from a real run of the Day 89 lab on the authoring machine on
2026-08-16, every timing is a best-of-seven with its median and spread beside
it, and the lesson says explicitly and repeatedly that the milliseconds are from
one machine on one day while the shape — a cost that grows with the table
against one that grows with its logarithm — is what generalises.

The material covered: what a scan does against what a seek does; the B-tree, its
fan-out and why depth grows so slowly; rowid tables and the implicit rowid
index; `CREATE INDEX` and unique indexes; reading `EXPLAIN QUERY PLAN`,
including the trap that `SCAN ... USING COVERING INDEX` names an index and is
still a scan; composite indexes and the leftmost-prefix rule demonstrated across
four query shapes; covering indexes; indexes that remove a sort; partial
indexes measured in pages; the five cases where a present index cannot be used —
a function, an expression, a leading wildcard, a prefix `LIKE` (which also
scans, and why), and an `OR` with one unindexed branch — with the fix for each
and an honest "there is no ordinary fix" where there is none; selectivity,
cardinality, `ANALYZE` and `sqlite_stat1`; the write cost and disk cost,
measured; and the judgement that the right number of indexes is the ones your
real queries need.

The A14 from-scratch requirement is met before any database appears: a linear
scan over a Python list against `bisect` over the same data kept sorted, over
inputs from a thousand to a million, **counting steps as well as timing them**
so the reader sees O(n) against O(log n) in output whose step counts are the
same on every machine.

The A13 alternatives section covers PostgreSQL (several index types — B-tree,
hash, GIN, GiST, BRIN — and `EXPLAIN ANALYZE` reporting estimated against
actual), MySQL and InnoDB (the clustered primary key and what it means for
secondary indexes), DuckDB (columnar storage and zone maps, where the answer to
"which index" is often "none"), and vector indexes as a deliberately restrained
forward reference to the retrieval work later in the course. Each has
when-to-choose-it, how to use it, one concrete example, and free versus paid
stated qualitatively. No price or tier is quoted anywhere.

The AI thread closes it: a retrieval system that cannot find the right thousand
rows quickly is a retrieval system nobody uses, the metadata filters on an
embedding store are exactly this problem, and the vector index later in the
course is the same idea with a different distance function.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with it:
the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

`query-plan-flow.svg` is animated with CSS `@keyframes` inside the file, so it
animates when rendered as an image and in the WordPress and MasterStudy export,
and prints as a still. It carries a `@media (prefers-reduced-motion: reduce)`
block that disables every animation and restores the resting state. Both SVGs
prefix every class, id and keyframes name — `d089a-` in the architecture diagram
and `d089f-` in the flow diagram — because the export inlines both files into
one HTML document, where a `<style>` block is not scoped to its own SVG and
`url(#name)` resolves document-wide.

Re-verify before changing any of them, and omit rather than approximate.
