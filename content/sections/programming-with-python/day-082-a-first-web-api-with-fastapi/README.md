# Day 082 — A First Web API with FastAPI

The fifth lesson of Week 12 ("Python for Automation and the Web"). Day 78 made
the learner an HTTP **client**; this lesson makes them the **server**, and it
opens on exactly that inversion — every status code, header and JSON body they
were reading is now something they choose and are answerable for.

It is also the payoff to a promise Days 70 and 75 made and could not keep.
Day 75 described pydantic as the runtime-value-validation complement to a
static type checker and moved on, because pydantic was not installed. **It is
installed now — version 2.13.4, verified on 2026-07-19 — and it arrived
exactly as the lesson says it does: as a dependency of FastAPI, which nobody
requested directly.** The lesson dwells on the moment an annotation stops
being documentation and starts causing validation to happen at runtime.

Covered in order: what a web API is and why a machine client makes the
contract matter more than the appearance; REST as conventions rather than a
standard, with the honest note that most real APIs are only loosely REST;
FastAPI concretely — the app object, a first path operation, running it under
uvicorn, path parameters with conversion, query parameters with defaults and
constraints, request bodies as pydantic models; the 422 and its structured
detail; response models and the leak they prevent; status codes chosen
deliberately including 201 with a `Location` and 204 with an empty body;
`HTTPException` and why a traceback must never reach a client; `Depends` as
Day 74's boundary argument with framework support; the generated OpenAPI
schema and why a machine-readable contract is the whole point; `async def` to
exactly the depth of "these can be coroutines and that matters when they
wait"; and a short security section — validation is not authorization, never
trust a client-supplied id, CORS is a browser mechanism, secrets come from the
environment. It closes on the AI thread: an inference endpoint is a POST with
a validated body, a response model, a timeout and a status code, and an
OpenAPI document is machine-readable in the same way a tool definition is.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no
  filler of any kind — if a fact or figure is not verified, leave it out
  rather than approximating it.
- **Every line of output in this lesson is a real capture from a real run on
  2026-07-19**, on macOS 26.5.1 with Python 3.14.0, fastapi 0.139.2, pydantic
  2.13.4, starlette 1.3.1, uvicorn 0.51.0, httpx 0.28.1 and pytest 9.1.1. Most
  come from the lab's `expected-output/`; the type-conversion and 500 examples
  come from short runs against `examples/type_demo.py`; and the uvicorn startup
  log is a genuine capture from a server that really was started on
  `127.0.0.1:8123` and stopped again. If you change a snippet, rerun it and
  recapture — never edit a quoted body by hand.
- **The pydantic version is load-bearing.** It was read from the installed
  package metadata rather than assumed, and the lab's test harness reprints
  every installed version and compares it against `requirements.txt`. Do not
  update the number here without rerunning.
- **Flask, Django, Django REST Framework and Litestar are NOT installed on the
  authoring machine.** The Alternatives section says so explicitly and quotes
  no output for them; their code examples are written in the shape their own
  documentation uses and are never presented as captured runs. Keep it that
  way unless somebody actually installs and runs them.
- Historical claims are deliberately specific and checkable: Fielding's 2000
  dissertation at UC Irvine, PEP 333 by Phillip J. Eby in 2003, ASGI from
  Andrew Godwin's Django Channels work, FastAPI by Sebastián Ramírez in 2018,
  Starlette and Django REST Framework by Tom Christie, pydantic by Samuel
  Colvin in 2017 with a Rust core in version 2, Flask by Armin Ronacher in
  2010, Django from the *Lawrence Journal-World* by Adrian Holovaty and Simon
  Willison in 2005, Swagger by Tony Tam at Wordnik donated to the Linux
  Foundation in 2015. Litestar is described as having begun as Starlite and
  been renamed, without a date, because that is the limit of what was
  verified. Do not add a fact here you have not checked.
- **No loopback-hostname URL anywhere.** The lesson refers to "the local test
  server" in prose and uses `127.0.0.1` with an explicit port only where a
  real captured log contains it.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the
  content.
- Keep image alt text in `index.mdx` and `visuals.yml` identical — including
  the absence of square brackets, which would terminate the markdown image
  syntax and break the rendered alt.
- When you revise any file in this directory, update `last_verified` in
  `lesson.yml` to the revision date.
- Regenerate any downstream exports (search index, print/PDF builds) after
