# Day 072 — Fixtures, Parametrization, and Test Design

The second lesson of Week 11 ("Testing and Code Quality"). Day 71 established
what a test is and how to prove one can fail; this lesson is about what
happens next, when there are forty of them. It covers the two kinds of
duplication a suite accumulates and the two different tools for them —
fixtures for repeated arrangement, parametrization for repeated assertion
shape — and then spends its second half on the judgment that keeps the cure
from being worse than the disease: choosing a scope by mutability rather than
speed, protecting test independence, and recognising the over-fixtured suite
that nobody can read.

The running example is a CSV-backed practice log, deliberately built from the
file-handling skills of Days 64–65 and the dataclass skills of Day 69, so the
only genuinely new material is the testing itself. Every number in the lesson
— 41 collected items, 11 selected by `-k refuses`, one session-scoped fixture
body running once while a function-scoped one runs four times — is captured
from a real run of the lab on the authoring machine.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout
from central configuration — never hard-code repository or site URLs inside
content files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler of any kind — if a fact or figure is not verified, leave it out rather than approximating it.
- Every captured output in the lesson comes from a real run of the Day 72 lab with pytest 9.1.1. If the lab's test files change, the collected counts change too — re-run and replace the captures rather than editing the numbers by hand.
- The counts are load-bearing and appear in five places: `index.mdx`, the lab README, `expected-output/FIELDS.md`, the lab's `tests/run_tests.sh`, and `metadata.yml`. Change one and check all five.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the content.
- Never write a tool path from the authoring environment into any content or lab file; captured output must be sanitised so no absolute home directory appears.
- When you revise any file in this directory, update `last_verified` in `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep the exact H2 heading strings intact — the lesson validator checks them.
- Keep `monkeypatch` deliberately light here: Day 74 owns mocking and testing at boundaries, and this lesson should introduce the fixture without pre-empting it.
