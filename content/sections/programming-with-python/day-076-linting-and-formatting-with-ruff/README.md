# Day 076 — Linting and Formatting with Ruff

The sixth lesson of Week 11 ("Testing and Code Quality"). It arranges four
quality gates over a Python codebase and says exactly what each one proves: a
**formatter** decides how code looks, a **linter** flags suspicious patterns, a
**type checker** (Day 75) proves the type claims, and a **test suite**
(Days 71–74) checks behaviour. Ruff is both the formatter and the linter, in one
binary. The lesson covers the history honestly — pycodestyle and pyflakes,
flake8 as the aggregator, pylint as the heavyweight, isort, Black's
un-configurable turn in 2018, then Ruff reimplementing hundreds of those rules
in Rust — then the mechanics: rule-code prefixes, `select` / `ignore` /
`extend-select`, per-file ignores, surgical `noqa` suppression, and the
safe-versus-unsafe autofix distinction. The second half is judgement: which
rules are genuinely worth enabling, why a team should start small and grow the
set, and the real failure mode of a lint configuration everyone has learned to
ignore. It is the direct successor to Day 61 (Writing Readable Code), which made
the same judgements by hand.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout
from central configuration — never hard-code repository or site URLs inside
content files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler of any kind — if a fact or figure is not verified, leave it out rather than approximating it.
- Every code output shown in the lesson is captured from a real run against Ruff 0.15.22, pytest 9.1.1 and Python 3.14.0, verified 2026-07-19. If the lab's example code changes, re-run the capture and replace the text rather than editing the numbers by hand.
- Speed figures are measurements, not benchmarks. State the hardware, never compare against a tool that was not run, and never quote a benchmark that cannot be reproduced on the machine at hand.
- Name only tools that were actually executed here. flake8, pylint, Black, isort and pre-commit are **not** installed on the authoring machine, and the Alternatives section says so plainly instead of inventing their output — keep that honesty if the section is revised.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the content.
- When you revise any file in this directory, update `last_verified` in `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep the exact H2 heading strings intact — the lesson validator checks them.
- This is a linting lesson, so the placeholder-marker scan is unusually easy to trip. Demonstrate rules only from the set this lesson already uses (`F401`, `F841`, `E501`, `E711`, `B006`, `SIM108`, `I001`, the `UP` family, `S101`, `PGH004`, `RUF100`); never introduce the reminder-comment rule families, and never write a placeholder marker into sample code or captured output.
- Regenerate any downstream exports (search index, print/PDF builds) after edits so rendered outputs match the source.
