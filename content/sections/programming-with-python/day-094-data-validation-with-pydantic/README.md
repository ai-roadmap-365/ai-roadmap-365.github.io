# Day 094 — Data Validation with pydantic

The fourth lesson of Week 14 ("Data Formats and Pipelines"), and the one the
week's project rests on. Day 92 taught the formats data arrives in; this day
is about what you do the moment it has arrived.

The organising idea: **a program's boundary is where data stops being your
problem and starts being your responsibility.** Everything crossing it — a
JSON body, a CSV row, an environment variable, a config file, a model's output
— is untrusted until something checks it. pydantic's contribution is that you
declare what "valid" means once, in the annotations you were writing anyway,
and have it enforced every time.

The day also completes a family the reader now knows and is usually taught as
rivals: **the type checker before it runs (Day 75), the validator as data
arrives (today), the database constraint as data is stored (Day 88)** — with
each layer's blind spot stated explicitly, because "the model already checks
it, drop the NOT NULL" is common advice and it is wrong.

The two places the lesson works hardest are the two places beginners are
actually ambushed. **Coercion** is demonstrated rather than described: a
twenty-row table, every cell the result of a real `TypeAdapter` call in lax
mode and again with `strict=True`, because the rule ("convert when the
conversion is unambiguous and loses nothing") only becomes memorable once you
have seen `"42.0"` accepted as an int and `42.7` refused. And **required
versus optional versus nullable** is treated as three separate facts with a
four-row table of the combinations, settled against
`model_json_schema()["required"]` rather than by argument.

The habit the day exists to instil: **assert on an error's `type` and `loc`,
never on its `msg`.** Day 82 made the same point about a FastAPI 422 body, and
it is literally the same structure. Every one of the lab's 47 reference tests
obeys it, and the harness greps to prove none of them cheat.

The day then lands where the week needs it: **validation as a data-quality
gate.** One bad record must not end the run. The gate meets a batch that is
two-thirds bad, keeps the four good records, refuses eight, counts both, and
writes a report naming every refusal with its `loc` and `type` — and can fail
the build when the reject rate crosses a threshold. Day 98's section project
depends on that pattern.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the
layout from central configuration; never hard-code repository or site URLs
inside content files.

`validation-flow.svg` is animated with CSS `@keyframes` inside the file, so it
animates wherever it is rendered as an image and prints as a still. It carries
a `@media (prefers-reduced-motion: reduce)` block that disables every
animation and restores the resting state, and the still frame carries the
whole meaning on its own — including the one real error entry, so a reader who
never sees the motion still learns the shape of a `ValidationError`. Both SVGs
prefix every class, id and keyframes name — `d094a-` in the architecture
diagram, `d094f-` in the flow diagram — because an inlined SVG's `<style>`
block is not scoped to that SVG and `url(#name)` resolves document-wide, so
two diagrams on one page would otherwise restyle each other.
