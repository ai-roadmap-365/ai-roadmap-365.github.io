# Day 086 — SELECT: Filtering, Sorting, and Aggregating

The second lesson of Week 13 ("SQL and Relational Databases"). Day 85 introduced
the relational model, SQLite's architecture, type affinity, and a first
`CREATE TABLE` / `INSERT` / `SELECT`. Today is the day the reader learns to ask
questions.

The organising idea is the **logical evaluation order** of a `SELECT` — FROM,
WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT/OFFSET — and the fact
that it is deliberately not the order you write it in. Every confusion later in
the day is derived from that one ordering rather than memorised: why an aggregate
is illegal in `WHERE`, why `HAVING` exists when `WHERE` already filters, and why
`ORDER BY` may use an alias that standard SQL forbids in `WHERE`.

The lesson covers `WHERE` with comparison and boolean operators (including the
`AND`-binds-tighter-than-`OR` trap, which is 5 rows against 8 in the lab data);
`LIKE` and `GLOB` and how they differ on wildcards and case; `IN` and `BETWEEN`;
NULL and three-valued logic worked through properly with a full truth table and
the three classic traps; `ORDER BY` with several keys and where NULLs land in
each direction; `LIMIT`, `OFFSET` and why `OFFSET` is linear in its own size;
`DISTINCT`; computed columns, aliases and the core scalar functions; the five
aggregates including the real difference between `COUNT(*)` and `COUNT(column)`;
`GROUP BY`, including grouping by an expression; `HAVING` versus `WHERE`; `CASE`;
and an honest note on the two places SQLite is more permissive than the standard.

The A14 from-scratch requirement is met by `examples/groupby_from_scratch.py` in
the lab, which implements grouping and all five aggregates as a dictionary of
accumulators in plain Python, then runs the one-line SQL that replaces twenty
lines and asserts the two results are identical. The A13 alternatives coverage
compares SQLite, PostgreSQL, MySQL/MariaDB, DuckDB, the Python standard library
and pandas on the same grouped query, with when-to-choose-it, how to run it, one
concrete example, and free versus paid stated for each.

The AI thread closes the lesson explicitly: every training-set statistic, every
evaluation summary and every "how many examples do we have of X" question is a
`GROUP BY`. Class imbalance is one query. A missing-data audit is
`COUNT(*) - COUNT(column)`. Per-slice evaluation is `GROUP BY slice` with the
denominator reported beside every figure — and the privacy note that a grouped
result with a bucket of one anonymises nothing.

cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

`select-evaluation-flow.svg` is an **animated** SVG per amendment A30. The
animation is CSS `@keyframes` inside the file, never SMIL and never a script,
because the file is referenced as an ordinary image and browsers do not run
scripts in an image document — but they do honour CSS media queries, which is
what makes the mandatory `@media (prefers-reduced-motion: reduce)` block work.
Every class, id and keyframes name in the two files is prefixed `d086a-` or
`d086f-` so that inlining both into one exported page cannot collide.
