# Day 091 — Designing and Querying a Real Schema

The seventh and final lesson of Week 13 ("SQL and Relational Databases"), and
the week's capstone. Days 85 to 90 taught the parts — the relational model,
`SELECT`, joins, writing data and constraints, indexes, and SQLite from
Python. This day is the synthesis: it teaches the *process* of turning a
paragraph of prose from somebody who has never heard the word "schema" into a
running database that answers real questions.

The through-line: **every design decision is a bet about which questions will
be cheap later.** So each decision is made explicitly and argued from both
sides — surrogate versus natural keys (with the three failure modes of getting
it backwards: the key changes, it is sometimes absent, it is sometimes
mistyped), when a many-to-many junction has earned attributes of its own, ISO
8601 text in UTC in a database with no date type, money as an integer count of
minor units, a CHECK constraint versus a lookup table for an enumeration,
every nullable column carrying a stated meaning, and soft delete priced
honestly as a per-query obligation.

The design half ends on the day's sharpest demonstration: a stored queue
position breaking silently in three ordinary statements, with no error raised —
which is the argument for refusing to store derived data, and the reason the
finished schema derives it with `ROW_NUMBER` instead.

The querying half then answers the questions the design exists for: scalar and
correlated subqueries; `EXISTS` against `IN` against a join, chosen by what
each returns, what each can multiply, and the `NULL` trap in `NOT IN`; common
table expressions, including a recursive one over a genuine hierarchy; window
functions for the top-N-per-group problem `GROUP BY` cannot solve; and views,
described honestly as buying a name and consistency but not speed. The whole
thing closes wrapped in a repository class from Day 90, printing a report a
person would actually read.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the
layout from central configuration; never hard-code repository or site URLs
inside content files.

`requirements-to-report-flow.svg` is animated with CSS `@keyframes` inside the
file, so it animates wherever it is rendered as an image and prints as a
still. It carries a `@media (prefers-reduced-motion: reduce)` block that
disables every animation and restores the resting state, and the still frame
carries the whole meaning on its own. Both SVGs prefix every class, id and
keyframes name — `d091a-` in the architecture diagram, `d091f-` in the flow
diagram — because an inlined SVG's `<style>` block is not scoped to that SVG
and `url(#name)` resolves document-wide, so two diagrams on one page would
otherwise restyle each other.
