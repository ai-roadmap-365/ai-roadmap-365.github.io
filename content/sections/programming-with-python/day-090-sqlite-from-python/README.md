# Day 090 — SQLite from Python

The sixth lesson of Week 13 ("SQL and Relational Databases"). Days 85 to 89
taught the relational model, `SELECT`, joins, writing and schema design, and
indexes — all of it through the `sqlite3` shell. Today the database moves
inside a program.

The through-line: **the shell was a place to explore; a program is a place
to be careful.** Two things go wrong in real code — string-built SQL and
misunderstood transactions — and both get a full mechanical demonstration
rather than a warning.

The lesson opens with one apostrophe leaking three private records and then
destroying a table, and with `with connection:` failing to close a
connection. It then covers the DB-API 2.0 object model and its origin (PEP
248 and PEP 249, Marc-André Lemburg, the `sqlite3` module by Gerhard Häring
added in Python 2.5); `sqlite3.connect` and the four per-connection
decisions a factory should make; cursors, `description`, `rowcount` and
`lastrowid`; the four ways to take rows out of a cursor with the memory cost
measured; `row_factory`, `sqlite3.Row` and a dict factory; parameter binding
in both styles with SQL injection taught by demonstration; `executemany`,
`executescript` and its transaction caveat; the transaction model precisely
— implicit handling, `with connection:`, `isolation_level`, `autocommit`,
`sqlite3.LEGACY_TRANSACTION_CONTROL` and `contextlib.closing`; `PRAGMA
foreign_keys` as per-connection and as a silent no-op inside a transaction;
the exception hierarchy produced by making thirteen deliberate mistakes;
threads and connections; adapters and converters with the deprecation status
reported from a real run; and the from-scratch data-access layer that keeps
SQL in one module and makes it testable per Day 74.

The Alternatives section covers the `sqlite3` module alone, a hand-rolled
repository, SQLAlchemy Core, the SQLAlchemy ORM, `pandas.read_sql` and
`aiosqlite` — each with when to choose it, how to use it, one concrete
example, and free versus paid. Four of the six are not installed on the
authoring machine, and the lesson says so rather than quoting output it did
not produce.

The AI thread closes it: every training run reads its data through code like
this, and the injection lesson generalises exactly one layer up — a system
that lets a model compose a query from text a user typed has the same
problem in a new costume, and the defence rhymes.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout
from central configuration — never hard-code repository or site URLs inside
content files.

`parameter-binding-flow.svg` is animated with CSS `@keyframes` inside the
file, so it animates when rendered as an image and in the WordPress and
MasterStudy export, and prints as a still. It carries a `@media
(prefers-reduced-motion: reduce)` block that disables every animation and
restores the resting state. Both SVGs prefix every class, id and keyframes
name — `d090a-` in the architecture diagram, `d090f-` in the flow diagram —
because the export inlines both files into one HTML document, where a
`<style>` block is not scoped to its own SVG and `url(#name)` resolves
document-wide.

The two caret lines inside the flow diagram rely on `xml:space="preserve"`
and a monospace font to line up with the statements above them. If you edit
either statement, recount the characters.
