# Day 097 — Logging and Configuration

The third lesson of Week 14 ("Data Formats and Pipelines"), and the one that
makes everything before it operable.

The organising idea: **`print` is for you, at your desk, right now; logging is
for whoever is awake when it breaks.** The lesson opens by making that concrete
— a working six-line script whose `print` statements are useless in production
because nothing records when they happened, which run they belong to, or what
severity they were, and which cannot be turned down without editing code. And
whose second line prints an API key.

The logging half teaches the thing most people never learn, which is the
module's **architecture**: loggers, handlers, formatters and filters as four
separate objects; the two-level rule that explains every confusing behaviour;
the dotted hierarchy and propagation, with the duplicate-message problem
demonstrated and then fixed two ways; the five levels chosen by asking who the
line is for; `exception()` against `error(str(e))`; lazy formatting measured
rather than asserted; structured JSON logging; `dictConfig`; rotation by size
and by time, with the honest note that stdout plus a supervisor is usually
better; and never logging a secret, with a redacting filter built and tested.

The configuration half builds the four layers — defaults, config file,
environment, command-line flags — **once, properly**, with the provenance of
every value printable, plus `tomllib`, the type problem, the missing-versus-
empty distinction, the twelve-factor argument and its limits, secrets, and
startup validation.

## Two findings, measured rather than assumed

This day contains two behaviours that contradict what most people (and most
tutorials) believe. Both were found by measurement while the lesson was
written, both are stated as measurements, and both are asserted by the lab's
test suite so that a change in a future Python fails the build rather than
quietly making this lesson wrong.

1. **A filter attached to a logger does not protect records propagating up from
   a child logger.** Propagation consults the ancestors' handlers, not their
   filters. Since every module calls `getLogger(__name__)` and is therefore a
   descendant, a redacting filter on the top-level logger protects almost
   nothing. It belongs on each handler.
2. **A secret inside an exception message survives a redacting filter**, because
   the traceback is rendered by the formatter after every filter has run.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the layout
from central configuration; never hard-code repository or site URLs inside
content files.

`config-precedence-flow.svg` is animated with CSS `@keyframes` inside the file,
so it animates wherever it is rendered as an image and prints as a still. It
carries a `@media (prefers-reduced-motion: reduce)` block that disables every
animation and restores the resting state, and the still frame carries the whole
meaning on its own — each of the four stages shows its own value and its own
provenance string, so the picture teaches without moving. Both SVGs prefix
every class, id and keyframes name — `d097a-` in the architecture diagram,
`d097f-` in the flow diagram — because an inlined SVG's `<style>` block is not
scoped to that SVG and `url(#name)` resolves document-wide, so two diagrams on
one page would otherwise restyle each other.
