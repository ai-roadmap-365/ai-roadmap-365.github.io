# Day 080 — Building CLIs with argparse

The third lesson of Week 12 ("Python for Automation and the Web"). Day 56 built
a data-driven command-line tool by reading `sys.argv` by hand; this lesson is
its direct sequel, and its argument is that a command line is a *user
interface* deserving the same care as a screen. It covers the anatomy of a good
command line and the conventions users already expect, `argparse` in depth
(types and validation, choices, defaults, nargs, actions, argument groups and
mutually exclusive groups), subcommands with `add_subparsers` and the
`set_defaults(func=...)` dispatch pattern, help output as a deliverable, exit
codes, reading from standard input, separating results from diagnostics,
`--dry-run` as a guarantee, configuration precedence, and testing a CLI both
in-process and as a subprocess. It closes on the AI thread: a tool schema
handed to a model is structurally the same declaration as `add_argument`, which
makes today the place that habit is built.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no
  filler of any kind — if a fact or figure is not verified, leave it out rather
  than approximating it.
- Every code output shown in the lesson is captured from a real run on the
  authoring machine. The `by_hand.py` counts, the `notes` help screens, the
  hashes around `--dry-run`, the `tiny.py` transcript in the hands-on section,
  and the `click` output in the Alternatives section were all executed. If the
  example code changes, re-run it and replace the captured text rather than
  editing it by hand.
- The Alternatives section states plainly which tools were installed on the
  authoring machine (`argparse` and `sys` as standard library, `click` 8.4.2 as
  an indirect dependency) and which were not (`typer`, `docopt`). Output is
  quoted only for the ones that were run. Keep that distinction if the
  environment changes.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the
  content.
- When you revise any file in this directory, update `last_verified` in
  `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, character for
  character, and keep the exact H2 heading strings intact — the lesson
  validator checks both. Alt text must contain no square brackets, which would
  terminate the markdown image syntax early.
- Keep the lesson's running example (the `notes` tool) aligned with the lab,
  which builds the same tool — this pairing is deliberate, unlike Day 70's
  split, because the value here is in implementing an interface the learner has
  already seen used from the outside.
- Regenerate any downstream exports (search index, print/PDF builds) after
  edits so rendered outputs match the source.
