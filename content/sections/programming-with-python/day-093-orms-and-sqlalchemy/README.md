# Day 093 — ORMs and SQLAlchemy

The third lesson of Week 14 ("Data Formats and Pipelines"), and the day Week
13's SQL becomes something a Python application can live with. Days 85 to 91
taught the relational model by hand: tables, joins, constraints, indexes,
parameter binding, and a schema designed from a paragraph of prose. This day
maps that schema onto objects — and spends most of its length on why the
mapping is harder than it looks.

The through-line: **an ORM maps rows to objects, and all of its difficulty
comes from objects and rows having different identities, different lifecycles,
and different ideas about when work happens.** Every section is a consequence
of that sentence. The identity map exists because two objects with equal
contents are two objects while two rows with one primary key are one row. The
Session exists because an object is alive when constructed and a row is alive
when committed. The N+1 problem exists because a relationship attribute looks
like a list and is a query.

The lesson is emphatic on one point and it is worth restating here: **an ORM
is not a way to avoid learning SQL.** This day only works because the reader
spent Week 13 writing SQL by hand. Every emitted statement in the lesson is
printed beside the Python that produced it, and the reader is expected to
judge whether the statement the ORM chose was any good.

From-scratch first (A14): before SQLAlchemy appears, the lab builds a working
ORM in about a hundred and sixty lines — column descriptors that learn their
own names through `__set_name__`, a metaclass that collects them, generated
`CREATE TABLE`, `INSERT` and `SELECT`, row-to-object mapping, and an identity
map. The reader who has written the toy understands the real library's
vocabulary immediately, and understands why the Session exists rather than
being told.

The measurement that changed the lesson: the brief expected a bulk operation
to show "dramatically fewer statements through Core than through the ORM". It
does not, on SQLAlchemy 2.0.51. A batched ORM insert and a Core insert both
cost **one** cursor execution for 500 rows, because the unit of work batches
into an `executemany` exactly as Core does. The lesson reports what was
measured, explains where Core *does* genuinely win (a bulk `UPDATE`, where the
ORM must build one Python object per matching row and Core builds none), and
says plainly that the round-trip argument for Core inserts is not supported by
the counter.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the
layout from central configuration; never hard-code repository or site URLs
inside content files.

`unit-of-work-flow.svg` is animated with CSS `@keyframes` inside the file, so
it animates wherever it is rendered as an image and prints as a still. It
carries a `@media (prefers-reduced-motion: reduce)` block that disables every
animation and restores the resting state, and the still frame carries the
whole meaning on its own. Both SVGs prefix every class, id and keyframes name
— `d093a-` in the architecture diagram, `d093f-` in the flow diagram — because
an inlined SVG's `<style>` block is not scoped to that SVG and `url(#name)`
resolves document-wide, so two diagrams on one page would otherwise restyle
each other.
