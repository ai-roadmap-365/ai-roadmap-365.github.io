# Day 073 — Test-Driven Development

The middle day of Week 11 ("Testing and Code Quality"), and the one about
*order*. Day 71 established why a suite is worth having and how pytest finds
and runs one; Day 72 established how to design tests that stay readable as
they multiply. Today the tests come first: write one small failing test, watch
it fail for the reason you predicted, write the least code that turns it
green, refactor against the net, repeat. The lesson's spine is a full
eight-cycle bowling kata with a real captured pytest run at every red and
every green, ending with the two tests that passed immediately and the
deliberate mutation that made them worth keeping. It is deliberately honest
about the practice being contested, and about the work — spikes, unknown
shapes, user interfaces, performance — where test-first does not pay.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout
from central configuration — never hard-code repository or site URLs inside
content files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler of any kind — if a fact or figure is not verified, leave it out rather than approximating it.
- Every pytest block quoted in the lesson is copied from a real capture in the lab's `examples/cycles/` directory. If the kata or the reference implementation ever changes, re-run it, re-capture, and replace the quoted text — never edit a summary line by hand.
- The history section is deliberately hedged where the record is thin (Beck's own account of rediscovering an older practice) and deliberately blunt where the record is clear (the 2014 "TDD is dead" argument, and the fact that the empirical literature disagrees with itself). Keep both. Do not add a study result or a percentage; none has held up well enough to print.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the content.
- When you revise any file in this directory, update `last_verified` in `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep the exact H2 heading strings intact — the lesson validator checks them.
- The lesson's worked kata and the lab's kata are the same one on purpose, because the day's whole claim rests on the learner reproducing captures they have already seen; keep them in step, and keep the lesson's practice assignment (Roman numerals) distinct from both.
- Regenerate any downstream exports (search index, print/PDF builds) after edits so rendered outputs match the source.
