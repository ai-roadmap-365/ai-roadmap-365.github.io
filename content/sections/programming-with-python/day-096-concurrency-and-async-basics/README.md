# Day 096 — Concurrency and async Basics

The second lesson of Week 14 ("Data Formats and Pipelines"), and the one the
rest of the week's pipeline work depends on, because a pipeline has a waiting
stage and a computing stage and has to choose correctly for each.

The organising idea: **concurrency is about structure, parallelism is about
hardware, and the mistake that costs people weeks is reaching for the wrong
one.** The whole decision reduces to a single question — *is this work
waiting, or is it computing?* — and the lesson's method is to make the reader
answer it by measurement rather than by assertion.

Every claim about speed on this day was measured on the authoring machine,
run three times, reported with its spread, and labelled as one machine on one
day. The two numbers the day turns on: the same three-line
`concurrent.futures` change gave **12.2x** on waiting work and **1.01x** on
computing work. What generalises is the sign of each comparison, never the
seconds, and the lab's tests assert only shapes with wide margins.

Three findings from the authoring runs are worth knowing before editing
anything here:

1. **The interpreter was checked, not remembered.** `Py_GIL_DISABLED` is `0`
   on this build — a standard interpreter with the lock. PEP 703's optional
   free-threaded build exists from Python 3.13 and is not what was used. The
   lab detects a free-threaded build and skips the one check that would be
   wrong there rather than failing it.
2. **The classic lost-update race did not reproduce at default settings.**
   Eight threads, fifty thousand increments each, zero lost across 20
   dedicated trials at the 5 ms switch interval. The lab reports that
   honestly and then lowers the switch interval to 1 microsecond, at which
   point the same unchanged code loses roughly 70% every run. The lesson
   draws the real conclusion: a concurrency bug's visibility is a property of
   timing, not of correctness, so you cannot test your way to confidence.
3. **asyncio on CPU-bound work measured 0.98x** — marginally slower than
   plain sequential code. That has not been rounded up to "about the same".
   An event loop that never gets an `await` is sequential execution plus the
   cost of running a loop.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the
layout from central configuration; never hard-code repository or site URLs
inside content files.

`event-loop-flow.svg` is animated with CSS `@keyframes` inside the file, so
it animates wherever it is rendered as an image and prints as a still. It
carries a `@media (prefers-reduced-motion: reduce)` block that disables every
animation and restores the resting state, and the still frame carries the
whole meaning on its own — both timelines, both queues, every task name and
every timing figure are drawn regardless of motion. Both SVGs prefix every
class, id and keyframes name — `d096a-` in the architecture diagram, `d096f-`
in the flow diagram — because an inlined SVG's `<style>` block is not scoped
to that SVG and `url(#name)` resolves document-wide, so two diagrams on one
page would otherwise restyle each other.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler — if a fact or figure is not verified, leave it out rather than approximating it.
- **Every timing figure quoted in this lesson is captured from a real run on the authoring machine on 2026-08-16**, offline, on the standard library only. The captures live in the lab's `expected-output/` directory. If you change a number here, re-run the lab and change it there too, and re-check `expected-output/FIELDS.md`, which states which values must match on any machine and which may differ.
- The environment facts are specific and were observed, not assumed: Python 3.14.0, `Py_GIL_DISABLED` = 0, 14 logical CPUs, default switch interval 0.005 s, macOS 26.5.2 on arm64. Re-verify before changing any version or GIL claim, and never describe free-threaded behaviour as though it had been observed here — it was not.
- **The race-condition finding is load-bearing and must not be softened.** The naive counter losing nothing at the default switch interval is the observation that earns the lesson's real point about testing concurrency. Do not replace it with a race that "works", and do not present the 1 microsecond switch interval as anything other than what it is: a way of making a real bug punctual.
- No performance number may be stated without the number of runs, the spread, and the machine. Ratios are the claim; seconds are context.
- The lab's tests assert shapes with wide margins and never a duration. If you add a claim to this lesson, add a shape assertion to the lab rather than a timing one.
- `trio`, `anyio`, `gevent` and Celery are described from their documentation only. **None is installed and no output from any of them is reproduced anywhere.** Keep it that way, and keep the "not installed here" labels attached.
- No prices, tier limits or free-tier allowances for any product may be written here. Celery's brokers are named without cost claims because none was verified.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the content. The only inline link in the body is the CAP theorem reference, which is in `sources.yml`.
- When you revise any file in this directory, update `last_verified` in `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep the exact H2 heading strings intact — the lesson validator checks them. Alt text must contain no square brackets: a closing bracket ends markdown image syntax and the alt renders broken.
- If you edit either SVG, keep every class, id and keyframes name behind its file's prefix (`d096a-` or `d096f-`), keep the `prefers-reduced-motion` block, keep both timelines drawn at the same scale so the comparison stays honest, and re-check with `xmllint --noout`.
- The coffee-shop analogy carries one prop — the baton, standing for the interpreter lock — through the whole lesson. If you extend it, check the mapping still holds: put the baton down for waiting, hold it for computing, a second shop for a second process, and the baton protecting the shop's books rather than your croissant count.
