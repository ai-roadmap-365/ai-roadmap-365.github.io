# Day 085 — Relational Databases and SQLite

The first lesson of Week 13 ("SQL and Relational Databases") and of the Data and
Databases subsection. It is the reader's first database, and it is written to
follow directly from Week 12: Day 84 shipped an automation toolkit that kept its
state in a JSON file, written atomically, and today measures exactly where that
stops paying.

The through-line: a file does not know what the data means, and everything a
database gives you follows from telling it.

The lesson opens by making the JSON file fail with numbers rather than argument
— 17 megabytes moved to change 27 bytes, a foreign key nothing rejects, two
atomic writers losing an update, and a question that costs a full parse and scan
every time. It then covers the relational model and its origin (Codd, IBM San
Jose, June 1970); relations, tuples, rows and typed columns; primary and
candidate keys and what a key actually guarantees; the schema as a promise the
engine keeps; SQL as a declarative language and why that is the entire point;
SQLite's architecture end to end from the C interface through the tokenizer,
parser, code generator and planner to the bytecode virtual machine, the B-tree
layer, the pager and the OS interface, and out to the single database file with
its rollback journal or write-ahead log; the file header read byte by byte;
SQLite's dynamic typing honestly, including a TEXT value living in an INTEGER
column and the comparison that silently drops it, with STRICT tables as the fix;
ACID one letter at a time, including which failure isolation prevents that Day
84's atomic write could not; the from-scratch query engine (restrict, project,
order_by) and the mechanical proof that SQL returns exactly the same rows; and
the first end-to-end walkthrough with dot-commands.

The Alternatives section covers SQLite, PostgreSQL, MySQL and MariaDB, DuckDB as
the analytical counterpart, and the commercial and managed tier — each with
when to choose it, a real command, one concrete example and free-versus-paid
stated qualitatively. No price, tier or allowance is quoted anywhere.

The AI thread closes it: every dataset, embedding store, evaluation log and
fine-tuning corpus lives in a database before it reaches a model, and the
retrieval half of retrieval-augmented generation is a query.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with it:
the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

`query-lifecycle-flow.svg` is animated with CSS `@keyframes` inside the file, so
it animates when rendered as an image and in the WordPress and MasterStudy
export, and prints as a still. It carries a `@media (prefers-reduced-motion:
reduce)` block that disables every animation and restores the resting state.
Both SVGs prefix every class, id and keyframes name — `d085a-` in the
architecture diagram, `d085f-` in the flow diagram — because the export inlines
both files into one HTML document, where a `<style>` block is not scoped to its
own SVG and `url(#name)` resolves document-wide.
