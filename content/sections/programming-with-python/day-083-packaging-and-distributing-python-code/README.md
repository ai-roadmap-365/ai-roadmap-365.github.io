# Day 083 — Packaging and Distributing Python Code

The sixth lesson of Week 12 ("Python for Automation and the Web"), and the day
the learner crosses from "code I run" to "code someone else installs".

Day 43 taught virtual environments and `pip` from the consumer side. Day 59
taught modules, imports and project layout. Day 77 wrote a `pyproject.toml` to
configure pytest, mypy, Ruff and coverage. Today the same file becomes package
metadata, and the same `main(argv) -> int` that Day 80 argued for becomes an
installed command.

The lesson covers the vocabulary carefully — module, package, distribution
package, project, and the constant split between distribution name and import
name — then sdist versus wheel and what is actually inside each,
`pyproject.toml` table by table and field by field, `[project.scripts]` and how
a package installs a COMMAND, the src layout and the genuine argument for it,
semantic versioning honestly (including that many projects do not keep the
promise), single-sourcing the version, dependency specifiers and the
library-ranges-versus-application-pins distinction, editable installs and what
they really put into `site-packages`, building with `python -m build` and
opening the wheel as the zip it is, `MANIFEST.in` and package data, and finally
publishing — described accurately, commands shown, and never performed.

The AI connection closes it: reproducibility is a packaging problem before it
is a modelling problem, and a model nobody can rebuild because nobody recorded
which versions produced it is an anecdote with a number attached.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata, and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay in sync with `visuals.yml`. All
cross-links (to the lab, to neighboring days) are generated by the layout from
central configuration — never hard-code repository or site URLs inside content
files.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no filler of any kind — if a fact or figure is not verified, leave it out rather than approximating it.
- **Nothing in this lesson or its lab may upload anything to any package index.** The publishing section shows commands and stops. That boundary is deliberate and must not be softened: a published version can never be reused, so an accidental upload has no undo.
- Every code output shown in the lesson is captured from a real run on the authoring machine. Tool versions named anywhere here or in the lab must match what was actually installed and verified (Python 3.14.0, `build` 1.5.0, setuptools 83.0.0, pip 25.2, pytest 9.1.1, verified 2026-07-19). Re-verify by running the tool before changing a number.
- The Alternatives section names hatch, hatchling, flit, poetry, uv, pipx and conda, none of which is installed on the authoring machine. It says so explicitly and quotes no output, timing or benchmark figure for any of them. Keep that disclosure intact and never add an unverified number.
- No prices or free-tier limits for any hosted service may be written here; the lesson says to read the provider's current terms instead.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in the content.
- When you revise any file in this directory, update `last_verified` in `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep the exact H2 heading strings intact — the lesson validator checks them. Alt text must contain no square brackets.
- Regenerate any downstream exports (search index, print/PDF builds) after edits so rendered outputs match the source.
