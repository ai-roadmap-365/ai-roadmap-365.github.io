# Day 139 — Reproducible Notebooks

The sixth day of Week 20 ("Working with Real Data"). It sits after Day 138
(data ethics, bias and provenance) and before Day 140, the week's project.

The through-line: **a notebook records what you ran, not the order you ran
it in — and those are different documents.** The lesson opens with a
three-cell notebook, built and executed for real, whose clean top-to-bottom
run answers `30.0` and whose out-of-order run — the order an analyst who
checked the report before adding a cleaning step actually used — answers
`50.0`, with no error either time. The rule the day defends: restart and
run all, or it did not happen.

## How this lesson is rendered

`index.mdx` provides the lesson body, and the sidecar YAML files travel with
it: the site layout renders the body at the day route, injects the quiz from
`quiz.yml`, the glossary from `glossary.yml`, and the source list from
`sources.yml`, and uses `lesson.yml` for navigation, metadata and time
estimates. Images are referenced from `index.mdx` with relative paths into
`assets/`, and their alt text must stay identical to `visuals.yml`. All
cross-links — to the lab and to neighbouring days — are generated by the
layout from central configuration; never hard-code repository or site URLs
inside content files.

`execution-order-flow.svg` is animated with CSS `@keyframes` inside the
file, so it animates wherever it is rendered as an image and prints as a
still. It carries a `@media (prefers-reduced-motion: reduce)` block that
disables every animation and restores the resting state, and the still
frame carries the whole meaning on its own. Both SVGs prefix every class,
id and keyframes name — `d139a-` in the architecture diagram, `d139f-` in
the flow diagram — because an inlined SVG's `<style>` block is not scoped to
that SVG and `url(#name)` resolves document-wide, so two diagrams on one
page would otherwise restyle each other.

## Editing rules

- Every file must ship complete: no stub text, no unfinished sections, no
  filler — if a fact or figure is not verified, leave it out rather than
  approximating it.
- Every output shown in this lesson is captured from a real run on the
  authoring machine on 2026-08-20, using nbformat 5.11.1, nbclient 0.11.0,
  nbconvert 7.17.1 and ipykernel 7.3.0 in this lab's own lab-local virtual
  environment (never the shared authoring venv, which does not have this
  stack). If you change a number here, re-run the capture and change it in
  the lab's `expected-output/` directory too.
- **The lesson's quoted outputs are verbatim, not retyped.** The clean and
  scrambled run comparison, the hidden-state transcript, the `nbconvert`
  Markdown sample and the environment record all come from
  `expected-output/scrambled-vs-clean.txt`, `expected-output/markdown-sample.md`
  and `expected-output/environment-record.txt`. Re-render before editing any
  of them.
- **The opening demonstration's execution order (`[0, 2, 1]`, not the day
  brief's illustrative "cell 3, then 1, then 3 again") is a deliberate,
  documented substitution, not a drift from the brief.** The literal
  sequence in the brief was tried against this lesson's actual three cells
  and raises `NameError`, because the third cell genuinely depends on a
  value only the first cell defines; forcing it to succeed would require
  pre-seeding the kernel from outside the notebook, which blurs this
  exercise into exercise 3's hidden-state mechanism instead of demonstrating
  pure out-of-order execution. See
  `labs/sections/math-statistics-and-data/day-139-reproducible-notebooks/expected-output/FIELDS.md`
  for the full account. Do not "fix" this by trying to force the literal
  sequence back in.
- **The output-stripping section reports a measured finding that
  contradicts common folklore, and that finding must not be softened.**
  Two fresh-kernel runs of identical, deterministic code have identical
  `execution_count` values; the field that actually differs is
  `cell.metadata.execution`. If you revise this section, re-measure before
  changing the claim.
- Jupyter Lab, papermill, Quarto and Google Colab are described from public
  documentation only. No output in this lesson is attributed to running any
  of the four; the Alternatives section and the metadata.yml honesty calls
  both say so explicitly, and no edit should imply otherwise without
  actually running them and re-pinning `requirements/requirements.txt` in
  the lab.
- Cite only sources listed in `sources.yml`; do not add URLs elsewhere in
  the content.
- When you revise any file in this directory, update `last_verified` in
  `lesson.yml` to the revision date.
- Keep image alt text in `index.mdx` and `visuals.yml` identical, and keep
  the exact H2 heading strings intact — the lesson validator checks them.
  Alt text must contain no square brackets: a closing bracket ends markdown
  image syntax and the alt renders broken.
- If you edit either SVG, keep every class, id and keyframes name behind its
  file's prefix (`d139a-` or `d139f-`), keep the `prefers-reduced-motion`
  block, and re-check with `xmllint --noout`.
- No LaTeX and no bare `{`/`<` in prose anywhere in `index.mdx` — MDX parses
  `{`/`}` as JSX and `<` as the start of a tag. Every code sample, JSON
  fragment and comparison operator in this lesson lives inside a fenced
  code block for exactly that reason; keep any addition the same way.
